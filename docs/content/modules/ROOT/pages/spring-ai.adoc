= Spring AI
:navtitle: Spring AI

`models-spring-ai` implements Spring AI's blocking and streaming `ChatModel`
contract over a Models `TextGenerationModel`. Both paths use the same
in-process tokenizer, chat template, generation loop, sampler, and selected
backend as plain Java.

Compatibility CI exercises Spring AI 1.1.4, 1.1.8, and 2.0.0. The application
normally selects the Spring AI version through its Spring AI BOM; the Models
adapter does not impose a provider or hosted model client.

== Dependencies

[source,kotlin,subs="attributes+"]
----
dependencies {
    implementation("org.springframework.ai:spring-ai-model:2.0.0")
    implementation("org.modeljars:modeljars:{modeljars-version}")
    implementation(
        "org.modeljars.huggingface:" +
            "ggml-org.qwen3-0.6b-gguf.q4_0:" +
            "3.0.0-q4_0.1"
    )
    implementation("com.integrallis:models-spring-ai:{models-version}")
}
----

== Blocking Chat

The adapter maps Spring AI system, user, assistant, and tool messages to the
selected Models chat template. Message text remains ordinary text and cannot
inject template control tokens.

[source,java]
----
import static org.modeljars.catalog.Qwen3_0_6b_Q4_0.MODEL;

import com.integrallis.models.api.SamplingOptions;
import com.integrallis.models.spring.ai.ModelsSpringAiChatModel;
import java.util.List;
import org.modeljars.ModelJars;

var defaults = SamplingOptions.builder()
    .temperature(0.0f)
    .maxTokens(128)
    .stopSequences(List.of("</answer>"))
    .build();

try (var runtime = ModelJars.openRuntime(MODEL)) {
    var model = new ModelsSpringAiChatModel(
        runtime.model(),
        runtime.descriptor().alias(),
        runtime.chatTemplate(),
        defaults,
        runtime.descriptor().capabilities());

    String answer = model.call("Answer using only the supplied context.");
    System.out.println(answer);
}
----

Use the chat template recorded by the exact qualified ModelJar rather than
selecting one from the architecture name.

== Observability

Pass the application's `ObservationRegistry` to keep local blocking and
streaming inference on Spring AI's standard `gen_ai.client.operation` surface:

[source,java]
----
var model = new ModelsSpringAiChatModel(
    runtime.model(),
    runtime.descriptor().alias(),
    runtime.chatTemplate(),
    defaults,
    observationRegistry,
    runtime.descriptor().capabilities());
----

The adapter reports `gen_ai.system=integrallis`, the Models runtime identity as
the request and response model, the operation duration, and failures. Every
`ChatResponse` carries the same model identity. A completed Models runtime
generation also reports exact counts through Spring AI's `Usage`: prompt tokens
are counted after applying the qualified chat template, and completion tokens
are the non-terminal tokens generated by the runtime.

[source,java]
----
ChatResponse response = model.call(new Prompt("Name one JVM language."));
var usage = response.getMetadata().getUsage();

System.out.printf(
    "prompt=%d completion=%d total=%d%n",
    usage.getPromptTokens(),
    usage.getCompletionTokens(),
    usage.getTotalTokens());
----

Custom `TextGenerationModel` implementations that only invoke the legacy
`TokenStream.onComplete()` callback remain compatible and retain Spring AI's
empty-usage behavior. Exact counts are reported by Models runtime generations.

Pass the selected catalog alias explicitly when the model file's embedded
metadata is generic or ambiguous. Constructors without that argument retain
the runtime's `modelName()` for source compatibility.

`setObservationConvention(...)` accepts an application-specific Spring AI
`ChatModelObservationConvention`. Constructors without an
`ObservationRegistry` retain their source-compatible no-op behavior.

== Tool Calling

When a `ChatClient` request declares Spring AI tools, the adapter renders their
names, descriptions, and input schemas into the selected Models chat template.
Model output is scanned back into Spring AI `AssistantMessage` tool calls. The
`ChatClient` executes the registered Java callback. Generative chat models
receive that result for a follow-up answer. Needle 2 is an action-selection
model, so its completed call returns the actual Java tool result instead of
asking the selector to choose the same action again. Needle action selection
always uses deterministic decoding; a chat-oriented temperature configured on
the adapter or request cannot turn an applicable action into a sampled refusal.

Pass the ModelJar descriptor capabilities when constructing the adapter. This
makes an artifact that was qualified for chat, but not tool calling, fail before
generation instead of silently attempting an unsupported workflow.

[source,java]
----
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.annotation.ToolParam;
import org.springframework.boot.ApplicationRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.stereotype.Service;

@Service
class WeatherTools {
    @Tool(
        name = "get-weather-for-zipcode",
        description = "Gets weather for a given zipcode")
    Weather getWeatherForZipcode(
        @ToolParam(description = "The zipcode to get weather for")
        String zipcode) {
        return new Weather(zipcode, "Raining cats and dogs", 78);
    }

    record Weather(String zipcode, String conditions, int temperature) {}
}

@Bean
ApplicationRunner weatherDemo(WeatherTools weatherTools) {
    return args -> {
        try (var runtime = ModelJars.openRuntime(MODEL)) {
            var model = new ModelsSpringAiChatModel(
                runtime.model(),
                runtime.descriptor().alias(),
                runtime.chatTemplate(),
                defaults,
                runtime.descriptor().capabilities());

            var chatClient = ChatClient.builder(model)
                .defaultTools(weatherTools)
                .build();

            String answer = chatClient.prompt()
                .user("What is the weather for 88252?")
                .call()
                .content();
            System.out.println(answer);
        }
    };
}
----

`defaultTools(...)` and per-request `.tools(...)` use the same adapter path.
For Needle 2, `answer` is the serialized `Weather` returned by the invoked
method. For a qualified generative tool-calling model, it is the model's
follow-up response after seeing that tool result. Release verification executes
this exact prompt against the pinned CACT artifact and asserts that the Java
method receives exactly `"88252"` before checking the serialized result.

GPT-OSS uses the Harmony protocol. The adapter recognizes both recipient positions
permitted by Harmony, renders current constrained-JSON call history, addresses named
tool results back to the assistant, and returns only the completed final-channel text.
The exact hyphenated weather example above is covered against the pinned official
GPT-OSS 20B checkpoint. That checkpoint demonstrates adapter compatibility but remains
outside the ModelJars catalog until its Java prefill meets the performance gate.

The same execution path is covered for blocking and streaming `ChatClient`
requests. Streaming with declared tools buffers generated text until the tool
call is complete, because Spring AI can only act on a complete request.

Calling the lower-level `ChatModel.call(Prompt)` API returns an
`AssistantMessage` containing the parsed tool calls; it does not execute Java
callbacks. Use `ChatClient` when the application wants Spring AI to own the
tool-execution loop.

When the wrapped model exposes a contrastive head and more than five tools are
declared, the adapter retrieves the five most relevant schemas before it
renders the prompt. Schema vectors are cached in a bounded per-adapter index;
subsequent requests embed the user query without re-embedding an unchanged
tool catalog. The selected schemas also define the decoding constraint.

== Schema-Constrained Tool Decoding

If the wrapped Models runtime implements `ConstrainedTextGenerationModel`, the
Spring AI adapter compiles supported tool input schemas into a token constraint
and passes it into the generation loop. Sampling then admits only tokens that
keep the output on a valid tool-call string. This changes tool calling from
"ask the model to follow the schema" to "prevent invalid enumerable tool-call
syntax from being decoded" for the supported schema subset.

For ChatML and Llama 3, the Spring AI adapter constrains finite tool-call
spaces:

* tool syntax must be one of the non-array-wrapped Models JSON formats, such as
  ChatML or Llama 3 JSON-native tool calls
* argument properties must be string `enum` values, or absent
* every `required` property must be one of those enumerable properties
* the compiled call set is capped to keep decoding checks bounded

Needle 2 has a separate array-aware grammar compiled directly from JSON Schema.
It supports objects, arrays, strings, integers, numbers, booleans, nulls,
`enum`, `const`, `oneOf`, and `anyOf`, with an explicit bound on optional-object
expansion. The decoder also prevents model protocol markers and JSON closing
delimiters from being consumed as plain string content, so malformed output
cannot reach a Java tool argument.

For example, this Spring AI input schema can be enforced during decoding:

[source,json]
----
{
  "type": "object",
  "properties": {
    "mode": {
      "type": "string",
      "enum": ["cool", "heat"]
    }
  },
  "required": ["mode"]
}
----

With a compatible chat template, the runtime constrains output to valid calls
such as:

[source,json]
----
{"name":"set_mode","arguments":{"mode":"cool"}}
----

or the template's tagged equivalent, for example:

[source,text]
----
<tool_call>{"name":"set_mode","arguments":{"mode":"cool"}}</tool_call>
----

Schemas that require open text, numbers, arrays, nested objects, conditionals,
references, or any other value space the adapter cannot enumerate are not
partially constrained. The adapter deliberately falls back to ordinary tool
calling for those schemas, leaving the generated call parser and Spring AI tool
execution path unchanged. That fallback preserves correctness for ordinary
Spring AI applications while keeping the enforced path honest about what it can
guarantee.

== Request Options

Non-null `ChatOptions` values override adapter defaults for temperature, top-p,
top-k, maximum tokens, and stop sequences. Values absent from the request retain
the Models defaults. A request `stopSequences` list replaces the default list
for that generation; repetition penalty and seed remain Models defaults because
Spring AI's common `ChatOptions` contract does not expose them.

[source,java]
----
import org.springframework.ai.chat.messages.UserMessage;
import org.springframework.ai.chat.model.ChatResponse;
import org.springframework.ai.chat.prompt.ChatOptions;
import org.springframework.ai.chat.prompt.Prompt;
import java.util.List;

var requestOptions = ChatOptions.builder()
    .temperature(0.2)
    .maxTokens(96)
    .stopSequences(List.of("</answer>"))
    .build();
var prompt = new Prompt(
    List.of(new UserMessage("Return one cited sentence.")),
    requestOptions);

ChatResponse response = model.call(prompt);
System.out.println(response.getResult().getOutput().getText());
----

`getOptions()` exposes the adapter defaults through Spring AI's `ChatOptions`
view, including the local Models runtime identity. Per-request overrides do not
mutate those defaults.

== Streaming Chat

`stream(Prompt)` returns a `Flux<ChatResponse>` whose elements contain decoded
token fragments in generation order. Models runs blocking inference on
Reactor's bounded-elastic scheduler so subscription does not block the
subscriber thread. A generation failure is propagated through the Flux error
signal without being wrapped or followed by completion. For ordinary text
generation, the terminal response has empty text and carries the complete
Spring AI `Usage`; concatenate text fragments and read usage from that terminal
response.

[source,java]
----
model.stream(new Prompt("List the retrieved facts."))
    .map(response -> response.getResult().getOutput().getText())
    .doOnNext(System.out::print)
    .doOnError(Throwable::printStackTrace)
    .blockLast();
----

The adapter does not close the underlying `TextGenerationModel`; the
application or Spring bean lifecycle owns it. Apple's system model implements
the same contract, but currently emits its complete response as one streaming
element because Apple's API returns a complete response to the bridge.

== Embeddings

`ModelsSpringAiEmbeddingModel` adapts a Models `EmbeddingBackend` to Spring
AI's `EmbeddingModel`.

[source,java]
----
import com.integrallis.models.api.EmbeddingBackend;
import com.integrallis.models.spring.ai.ModelsSpringAiEmbeddingModel;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.ai.embedding.EmbeddingModel;

@Bean(destroyMethod = "close")
EmbeddingModel localEmbeddingModel(
        EmbeddingBackend backend,
        ObservationRegistry observations) {
    return new ModelsSpringAiEmbeddingModel(
            backend, "embeddinggemma-300m-q8_0", observations);
}
----

This adapter owns the backend it wraps and closes it. See
xref:embeddings.adoc[Embeddings] for producing the backend. Passing Spring's
`ObservationRegistry` records standard `gen_ai.client.operation` observations
for direct, document, and batch embedding calls. The pinned model name and
backend dimension are attached to each observation and response. Concurrent
framework calls are serialized around the backend because the local encoder
reuses mutable scratch state between sequences.

For auto-configuration, named-bean behavior, and combined Models/Vectors setup,
continue with xref:spring-boot.adoc[Spring Boot]. For validation after
retrieval, see xref:rag.adoc[RAG Validation].
