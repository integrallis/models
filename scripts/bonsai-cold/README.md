# Fixed Bonsai whole-model convolution follow-up

This prepared protocol compares the actual Bonsai qwen35 model using two Vectors artifacts and the same composed Models runtime. Dispatch is held until the final Vectors candidate passes its component screen; the prepared Vectors identity is source `b0aadc8d972f3504426f6e38fcb0a4b4a97a0333`, core SHA-256 `263bff1aef74bac56d0597ba6b4d7ad52af846fac08b32e70e5d549ce5c8f099`, including the measured BF16 row-boundary repair; final release gates remain open. Models is pinned to `5344b5a2ff84a27548f0f2c4840c24f22d73c32d`, including exact native-width dot, Q5 decoder, attention and PTQ repairs. `models-correspondence.json` records the two additional class changes since the previous dot/decoder composition. Both comparison arms receive these Models repairs; this isolates Vectors changes and is not a comparison against the previous published Models runtime. Native libraries, weights, datasets, JDK, heap, worker configuration and the Java workload retain the prior protocol. Complete entry manifests and actual loaded-JAR receipts must match.

Ten independent hosts per architecture each run one matched pair, with five baseline-first and five candidate-first orders. At most ten hosts run concurrently. Both fixture processes, the first timing process and the second timing process have separate retained artifacts. A process is bounded to 80 minutes; a host job is bounded to 330 minutes. Failed or incomplete observations remain visible and cannot be replaced. Candidate fixture failure blocks its timing. The known published fixture failure remains recorded and does not block timing.

Every timing process retains one cold request, three warmups and three measured requests, eight generated tokens and nine owned full-vocabulary logit snapshots per request. Across ten pairs this covers 15 JEVBench and 15 SNIPS tasks. Candidate results must stay exact across repeated tasks and compilation/session/process contexts. Both dataset quality counts must be at least their matched baseline counts.

The seven original metric limits and maximum confidence-interval width remain unchanged. A new explicit metric takes `javaAllocatedBytes` from the first request (`repeat=-4`), with the same 1.01 resource-ratio upper limit and 0.02 interval-width requirement. Cold allocation is not inferred from warm allocation. The 20,000-resample bootstrap resamples ten matched host-pair log ratios together with seed 716309. Singleton within-host strata would erase uncertainty and are deliberately not used.

The ten-pair count is fixed before results. It gives the first affected whole-model evidence quickly; it is not a promise that every precision target will pass. Wide intervals remain unresolved. Earlier observations are retained separately; no pooling, optional stopping or changing acceptance limits is permitted. A later fixed precision cohort may be planned from complete prior evidence.

Qwen2.5 does not use the changed convolution route, but the composed Models runtime now changes its dot/decoder implementation on narrow-vector hosts. The previous 320/160-pair result remains scoped to its original Models and Vectors artifacts. Entry correspondence alone does not qualify this new composition.

## Dispatch preparation

`freeze_runtime.py` updates only the reviewed Vectors revision, complete core checksum, phase label and candidate entry manifests. It rejects a wrong candidate checksum and requires the original `13f0` Qwen artifact for explicit entry correspondence. It does not alter workload, pair counts, metrics, limits, bootstrap or fixture rules. `freeze_models` separately accepts only the three reviewed dot/decoder class changes and updates both arms together; it rejects any additional runtime entry change before writing. Review the source reachability of every changed entry before relying on unaffected-path evidence.

The workflow now requires explicit dispatch so a preparation push cannot accidentally launch a rejected candidate. Its matrix alternates x86/ARM and records CPU affinity, physical resource limits and memory. Launch only after the exact candidate passes the supported-host component screen. All historical rejected results stay outside the repository.
