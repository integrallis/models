# V9 failure analysis and V10 hypothesis

V9 is rejected, not nearly qualified. On the fixed 75-case development screen it reached 88%
exact tool selection versus 86% for the base, but only 98.67% syntax, 98.67% schema validity, and a
24% irrelevance false-call rate.

The six parseable false calls were capability-boundary errors:

| Request | Incorrect tool selected |
| --- | --- |
| Similar blue paint color | `color_complimentary` |
| Author of *Don Quixote* | `music_composer.composition_info` |
| Projected company loss | `finance.predict_revenue` |
| Gas generated by heating a chamber | `thermodynamics.calc_gas_pressure` |
| Symbolic magnetic field around a wire | `magnetic_field_intensity` with invented values |
| Instrument family of a cello | `get_instrument_info` |

A seventh irrelevance case attempted six unsupported happiness-index calls and was truncated,
causing the single syntax and schema failure. The errors are not random formatting noise: the model
recognized nearby words in callable names, then ignored narrower descriptions or missing required
facts.

Hammer's pinned preparation code masks function and parameter names for approximately two thirds
of its examples. That creates direct evidence that the target can be learned from descriptions and
schemas rather than memorized API identifiers. V10 implements only that mechanism, deterministically
and with collision checks, on the existing contamination-controlled corpus. The fixed smoke will
show whether it reduces V9's false positives without sacrificing exact valid calls. Thresholds are
unchanged, and failure ends this candidate before the hidden window or JVM qualification.
