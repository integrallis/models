# What the ONNX executor was missing against onnxruntime, operator by operator

**Measured here, 2026-11-03, on the dev box (Intel Core i7-9750H, 6 cores, AVX2, no AVX-512),
while other sessions loaded it (load average 9 to 18). Same-session pairs only; absolute speeds
from this box are not the throughput gate, which is measured on a quiet box against a released
library (`experiments/paradee-8m-tts/README.md`).**

## Question

The released models 0.5.12 runs Paradee-8M at 0.45 to 0.48 of onnxruntime's speed on one thread
(quiet EC2 box, `experiments/paradee-8m-tts/evidence/box-0.5.12/`). Which operators carry the
difference, and what does onnxruntime do in each that the executor does not?

## Method

- **onnxruntime 1.23.2**, the publisher's package and session, one intra-op thread, its built-in
  profiler (`tools/ort_profile.py`): 50 Harvard sentences (`raw/harvard-50.json`), voice
  `af_heart`, with graph optimizations on and off. Kernel time per operator in
  `raw/ort-optimizations-*/summary.json`; per operator and input shape in
  `raw/ort-optimizations-off/by-op-shape.json` (`tools/aggregate_ort_profile.py` over the raw
  40 MB profile, which `tools/ort_profile.py` regenerates).
- **The executor**: the released `ParadeeLatencyArm` on the same 50 sentences, with
  `models-backend-onnx` swapped for a build carrying `tools/per-op-timing.patch` (a `nanoTime`
  around each `Operators.apply`, never committed to the library). Every run's `pass.json` names its
  route; all ran on `onnx-kernels=rust-ffm`.
- The source each finding cites is onnxruntime at tag v1.23.2 (`a83fc4d`), read at the cited
  file and function, and the executor at the cited class.

## Graph fusion is not the gap

Turning onnxruntime's graph optimizations off costs it only 17.0x to 16.0x real time
(`raw/ort-optimizations-*/summary.json`). The difference is in the kernels, operator for
operator, so the comparison below is against the unoptimized session, node for node.

What the code shows for each, worst first:

- **Pad (57x), Transpose and Slice (8x).** Every element went through `Tensor.copyElement`, a
  storage-kind dispatch per element; reflect Pad also mapped every element through a lambda with
  `floorMod`. onnxruntime copies contiguous runs (`transpose.cc`, `memcpy` of blocks; `pad.cc`,
  `PadAxis` and the flattened inner axis). Paradee's seven Pad nodes are all `reflect` on a
  single-channel waveform of about 65,000 samples.
- **Pow (43x).** The graph's only exponents are 3.0 (six nodes) and 2.0 (two nodes); the executor
  called `Math.pow` through a double lambda. onnxruntime's `PowImpl` (`element_wise_ops.cc`)
  turns exactly those two into `x * x * x` and `x * x`.
- **Erf (23x), Tanh (39x), Exp (21x), LeakyRelu (18x).** Erf called `libm::erf` in double
  precision once per element in Rust; the others were scalar `Math` calls through a
  `DoubleUnaryOperator`. onnxruntime evaluates MLAS's vector approximations (`MlasErfKernel`,
  `MlasTanhKernel`, `MlasComputeExpVector`, `MlasLogisticKernel`).
- **LSTM (5x).** One dot product per gate per timestep for the input side and scalar `Math.tanh`
  per gate. onnxruntime computes the input side of every timestep as one GEMM
  (`uni_directional_lstm.cc`, `ComputeGemm` over all rows) and applies `MlasComputeLogistic` and
  `MlasComputeTanh` (`rnn_helpers.cc`).
- **Mul (1.9x).** Paradee's largest Mul broadcasts `[1, 64, 1]` against `[1, 1, 64800]`. With the
  scalar run on the left, the executor fell to a loop dispatching on the operator per element; the
  other orientation already had a vector path.
- **MatMul (2x).** `[1, 433, 8, 80] x [80, 301]` ran as 433 products of 8 rows. onnxruntime's
  MatMul helper folds a shared right-hand matrix into one product over all rows.
- **Conv (1.5x).** Not the algorithm: for the STFT convolution (602 filters of 600 taps, stride 150,
  one input channel) MLAS also chooses expand-then-GEMM (`convolve.cpp`, `MlasConvPrepare`), and
  its depthwise kernel is compiled for WebAssembly only, so grouped convolutions are per-group
  im2col and GEMM there too (`conv.cc`). The remaining difference is the GEMM: MLAS's FMA3 kernel
  is a 6-row by 16-column broadcast tile (`FgemmKernelFma3Common.h`); the executor calls
  `matrixmultiply` 0.3.11, an 8 by 8 kernel, which compiles its AVX-512 kernel in by default.
- **Sine and ConvTranspose** are at parity already.

## What changed

- `Tensor.copyStrided` and `Tensor.gatherRow` resolve the storage kind once per row: one
  `System.arraycopy` for a unit stride. Transpose, Slice, Concat, Gather, Expand, ConstantOfShape,
  constant Pad and `Resampling.remap` (Resize, reflect and edge Pad) copy rows; reflect and edge Pad
  copy the unpadded middle whole and map only the edges. `RowCopyEquivalenceTest` checks
  Transpose, Slice and Pad against per-element definitions over 900 randomized cases.
- `Pow` by 2 and 3 as products formed in double and rounded once (the square is bit-identical to
  the general path).
- MLAS's exp, tanh, logistic and erf, translated with their constants verified bit for bit:
  `jmodels_onnx_{exp,tanh,logistic,erf}_f32` in Rust (replacing the per-element libm erf and the
  `libm` dependency) and `VectorMath` in Java as the fallback. `NativeOnnxKernelsTest` asserts the
  two produce identical bits. Routed through `Activations`.
- LSTM: one GEMM for the input side of the whole sequence; gate activations through `Activations`.
- Float arithmetic with a broadcast scalar on the left uses the vector kernels.
- MatMul folds a contiguous batch over a shared right-hand matrix into one product.
- im2col writes each column row once instead of zero-filling it first.

## Why the activations are native and not only Vector API

`VectorMath` is fast once C2 has compiled it, but not before.

From a cold JVM, `Elementwise.erf` on Paradee's GELU shape `[1, 216, 480]` with no kernels bound
(`raw/cold-start-vectormath-erf.txt`, `tools/cold-start/Cold.java`): the first call took 293 ms,
the next five 28 to 69 ms each, and compiled calls 0.22 to 0.24 ms.

The first sentences a speech model synthesizes would pay that, which is time to first audio, so
the native exports are the default route and `VectorMath` is the fallback where the library is
absent.

## A kernel that did not help, published as such

An MLAS-style AVX2 GEMM (6 x 16 tile, packed 16-column B panels, K blocks of 256) was written and
checked against a reference, then measured alternately with `matrixmultiply` in one process on the
STFT shape: no faster on this box, so it is not in this change. The box's load made the absolute
figures swing by up to 2x between rounds, so no GEMM figure is reported here; the GEMM question is
open, and on the quiet gate box (AMD EPYC with AVX-512) `matrixmultiply` already selects its
AVX-512 kernel.

comparison and division operators (Less, Div, Cos), which still run as scalar loops.
