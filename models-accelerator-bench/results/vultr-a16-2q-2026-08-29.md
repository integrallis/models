# Java/Tornado Q4 accelerator experiment — 2026-08-29

## Hardware and controls

Accelerator host:

- NVIDIA A16-2Q virtual GPU, 2 GiB VRAM, driver 550.90.07
- 2 Intel Cascade Lake vCPUs and 8 GiB host RAM
- Ubuntu 24.04, Temurin JDK 25.0.3, TornadoVM 5.2.0-jdk25 PTX backend

Stronger CPU control:

- 8 vCPUs (4 cores / 8 threads), AMD EPYC Milan
- Temurin JDK 25.0.3, 256-bit Vector API provider

All comparisons use the Models 0.3.14 source tree and released `vectors-core` dependency selected by
that tree. The full-model test uses the qualified Qwen3 0.6B Q4_0 GGUF. The GPU changes only eligible
Q4_0 prefill projections; tokenization, attention, sampling, KV state, decode, and all other model
work remain in the existing Java implementation.

## Isolated projection result

Shape: 3,072 rows × 1,024 columns. Weights remain on the device after first execution. GPU timings
include host Q8_0 activation preparation, host-to-native staging, device transfers, kernel execution,
and output copy.

| Batch | Relative L2 | GPU end-to-end p50 | 2-vCPU Vector API p50 | Speedup |
|---:|---:|---:|---:|---:|
| 1 | 1.59e-7 | 0.844 ms | 0.956 ms | 1.13× |
| 2 | 1.56e-7 | 0.916 ms | 1.337 ms | 1.46× |
| 4 | 1.52e-7 | 1.034 ms | 2.501 ms | 2.42× |
| 8 | 1.52e-7 | 1.366 ms | 3.767 ms | 2.76× |
| 16 | 1.53e-7 | 1.899 ms | 4.267 ms | 2.25× |
| 32 | 1.52e-7 | 3.054 ms | 7.959 ms | 2.61× |
| 64 | 1.53e-7 | 5.568 ms | 16.198 ms | 2.91× |

The first nested integer-reduction formulation passed JVM tests but failed the PTX device gate. A
flattened correctness fallback passed but was slower than the Vector API. Explicitly expressing the
16 packed Q4 pair products preserved integer arithmetic, passed the device gate, and produced the
measurements above. The qualification threshold was never weakened.

## Grouped projection result

The next checkpoint groups the two gate/up projections and the three Q/K/V projections. Each group
quantizes and transfers its activation once, uses one persistent execution plan, and returns each
projection through its existing output buffer. A deterministic PTX gate compared every output with
the released Vector API implementation:

| Dispatch | Output | Relative L2 |
|---|---|---:|
| dual | first | 7.83e-8 |
| dual | second | 9.30e-8 |
| triple | first | 7.83e-8 |
| triple | second | 9.30e-8 |
| triple | third | 4.49e-8 |

Refactoring the original explicit reduction into a helper initially crossed TornadoVM's 600-node
inline limit (631 nodes, then 799 after a first split). Dividing each row dot product into explicit
low- and high-nibble reductions kept both helper graphs below the limit and passed the unchanged
2.0e-5 relative-L2 gate on PTX.

For comparison, the simpler Q8_0-by-F32 experiment reached 2.70× at batch 1 and 10.61× at batch 32
against the same two-vCPU host. Q4_0 is the more relevant result because it exercises the activation
quantization and packed arithmetic used by published Q4_0 models.

## Full Qwen model result

The 30-token prompt has a deterministic expected answer of `JAVA` on both paths.

| Path | Prefill | TTFT | Total | Output |
|---|---:|---:|---:|---|
| A16 host, Vector API cold | 2.348 s | 2.360 s | 2.549 s | `JAVA` |
| A16 host, Vector API warm | 1.154 s | 1.155 s | 1.265 s | `JAVA` |
| A16 host, Tornado cold | 9.058 s | 9.060 s | 9.193 s | `JAVA` |
| A16 host, Tornado warm | 0.488 s | 0.489 s | 0.623 s | `JAVA` |
| 8-vCPU EPYC, Vector API warm | 0.574 s | 0.576 s | 0.651 s | `JAVA` |

The provider created 191 persistent projection plans. Compilation dominates its first request;
after compilation, prefill is 2.36× faster than the same host's warm Java path. Against the stronger
eight-vCPU control, this small model and short prompt are close: GPU total latency is only about 4%
lower.

The 250-token case produces identical text on CPU and GPU, although the tiny model does not follow
the requested one-word format. This case measures parity and throughput, not answer quality.

| Path | Warm prefill | Warm total |
|---|---:|---:|
| A16 host, 2-vCPU Vector API | 9.537 s | 9.928 s |
| A16 host, Tornado | 4.759 s | 5.047 s |
| 8-vCPU EPYC, Vector API | 4.951 s | 5.076 s |

The longer prompt required two batch shapes and 382 persistent plans. The 2 GiB A16 slice again
roughly matches the stronger CPU rather than decisively beating it.

Grouping reduces plans and Java-to-device dispatches by about 43% without changing generated text:

| Prompt | Original plans | Grouped plans | Original calls | Grouped calls |
|---|---:|---:|---:|---:|
| 30 tokens | 191 | 109 | 382 | 218 |
| 250 tokens | 382 | 218 | 3,056 | 1,744 |

| Prompt | Grouped Vector warm prefill | Grouped Tornado warm prefill | Grouped Tornado warm total |
|---|---:|---:|---:|
| 30 tokens | 1.116 s | 0.492 s | 0.629 s |
| 250 tokens | 9.734 s | 4.784 s | 5.062 s |

Warm latency is effectively unchanged from the ungrouped experiment (0.488 s and 4.759 s prefill).
The result removes redundant activation preparation and cuts plan bookkeeping, but projection
arithmetic and the remaining host work still dominate. Cold prefill also remains about nine seconds;
fewer, larger plans do not by themselves solve device compilation latency.

## Fixed-shape readiness result

TornadoVM 5.2 keeps compiled PTX only for the life of an execution plan. The prior provider also
specialized plans to the size of each prompt chunk, so a new remainder size compiled a second set of
plans. The follow-up uses a fixed 32-token device shape, zero-pads the unused rows, and copies back
only the requested rows. An explicit readiness prefill creates and compiles every projection plan,
then resets model state before the first visible request.

The unchanged 30-token prompt produced `JAVA` on every path:

| Stage | Prefill / readiness | TTFT | Total | Plans after stage |
|---|---:|---:|---:|---:|
| Vector API warm | 1.094 s | 1.096 s | 1.213 s | n/a |
| Tornado lazy first request | 9.430 s | 9.432 s | 9.612 s | 109 |
| Tornado readiness | 5.849 s | n/a | n/a | 109 |
| Tornado first visible after readiness | 0.551 s | 0.553 s | 0.887 s | 109 |
| Tornado warm | 0.523 s | 0.524 s | 0.601 s | 109 |

The first visible TTFT is within 6% of the immediately following warm request. Compilation still
costs 5.8–9.5 seconds on this A16 slice, but it is now a bounded readiness cost rather than an
unpredictable first-user penalty.

The 250-token prompt also retained its CPU/GPU output parity and reused exactly the same 109 plans:

| Stage | Prefill / readiness | TTFT | Total | Plans after stage |
|---|---:|---:|---:|---:|
| Vector API warm | 9.815 s | 9.824 s | 10.158 s | n/a |
| Tornado readiness | 9.482 s | n/a | n/a | 109 |
| Tornado first visible after readiness | 4.916 s | 4.919 s | 5.397 s | 109 |
| Tornado warm | 4.781 s | 4.783 s | 5.068 s | 109 |

This removes the prompt-remainder compilation defect and cuts the long-prompt plan count from 218
to 109. It does not make readiness free or broaden acceleration beyond Q4_0 projections; those are
separate release gates.

## CPU fallback follow-up

A five-second JFR sample spanning the end of Tornado compilation and its warm request still placed
the Java Q4_0/Q8_0 row dot first among sampled application methods. This includes small or decode
shapes that the experimental GPU threshold intentionally leaves on the CPU. Before changing Vectors,
the existing Java-only candidates were measured on this host with a 3,072 x 1,024 production shape:

| Temurin JDK 25 / Intel Cascade Lake | Average | Normalized allocation |
|---|---:|---:|
| widened production kernel, 256-bit cap | 0.509 +/- 0.021 ms | 93 B/op |
| signed-short pairwise candidate | 0.604 +/- 0.057 ms | 80 B/op |
| unsigned zero-point candidate | 2.467 +/- 0.100 ms | 23.9 MB/op |
| widened production kernel, 512-bit opt-in | 0.503 +/- 0.009 ms | 94 B/op |

The widened default remains correct for this C2/Intel profile. The signed-short kernel's previously
recorded gain is specific to its qualified GraalVM configuration, the unsigned formulation still
fails its allocation gate, and the 512-bit opt-in is within noise. No Vectors default or release is
justified by these measurements.

## Attention and decode decisions

The scalar and workgroup-tiled Java attention kernels both passed their isolated numeric gates. The
tiled kernel reached relative L2 `3.47e-7` and an isolated `1.31x` speedup, but failed the real-model
gate: for the 250-token prompt, warm prefill regressed from `4.781 s` with projection-only dispatch
to `10.266 s`. The production candidate therefore keeps attention and its KV-cache work on the
Vector API path for this device.

Single-token Q4 projection plans passed the full-model decode gate. Across an exact eight-token
greedy sequence, output tokens matched the Vector API path and median per-token latency improved
from `101.131 ms` to `64.298 ms` (`1.57x`); total decode time fell from `820.697 ms` to
`527.424 ms`. Eager readiness compiled both shapes in `14.389 s` and the model retained 223 device
plans. This path is eligible for productization subject to memory-capacity and device-selection
checks.

## Decision

The experiment proves that a Java-authored, in-process GPU backend is technically viable and can be
injected through the existing Models SPI without changing user inference code. It is not ready to
publish:

- readiness now contains first-request compilation and fixed-shape plans prevent recompilation for
  different prompt remainders, but startup remains several seconds;
- Q4 acceleration alone leaves attention and other Java work as the full-model limit;
- grouping removed 43% of the plans, but plan reuse or ahead-of-time caching is still needed to
  avoid one compiled plan per remaining tensor; and
- qualification must cover larger GPU allocations and additional vendors before choosing automatic
  eligibility thresholds.

The next experiments should retain the Java-first approach: profile the grouped full-model path,
test whether device-side activation preparation pays for its larger transfer, then measure attention
and KV-cache kernels. A larger Vultr A16 allocation was provisioned for the control but completed in
a stopped state and would not accept a power-on request; it was deleted without producing data.
