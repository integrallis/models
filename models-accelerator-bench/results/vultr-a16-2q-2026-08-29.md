# Java/Tornado Q4 accelerator experiment — 2026-08-29

## Hardware and controls

Accelerator host:

- NVIDIA A16-2Q virtual GPU, 2 GiB VRAM, driver 550.90.07
- 2 Intel Cascade Lake vCPUs and 8 GiB host RAM
- Ubuntu 24.04, Temurin JDK 25.0.3, TornadoVM 5.2.0-jdk25 PTX backend

Stronger CPU control:

- 8 vCPUs (4 cores / 8 threads), AMD EPYC Milan
- Temurin JDK 25.0.3, 256-bit Vector API provider

All comparisons use the Models 0.3.14 source tree and released `vectors-core` dependency selected by
that tree. The full-model test uses the qualified Qwen3 0.6B Q4_0 GGUF. The GPU changes only eligible
Q4_0 prefill projections; tokenization, attention, sampling, KV state, decode, and all other model
work remain in the existing Java implementation.

## Isolated projection result

Shape: 3,072 rows × 1,024 columns. Weights remain on the device after first execution. GPU timings
include host Q8_0 activation preparation, host-to-native staging, device transfers, kernel execution,
and output copy.

| Batch | Relative L2 | GPU end-to-end p50 | 2-vCPU Vector API p50 | Speedup |
|---:|---:|---:|---:|---:|
| 1 | 1.59e-7 | 0.844 ms | 0.956 ms | 1.13× |
| 2 | 1.56e-7 | 0.916 ms | 1.337 ms | 1.46× |
| 4 | 1.52e-7 | 1.034 ms | 2.501 ms | 2.42× |
| 8 | 1.52e-7 | 1.366 ms | 3.767 ms | 2.76× |
| 16 | 1.53e-7 | 1.899 ms | 4.267 ms | 2.25× |
| 32 | 1.52e-7 | 3.054 ms | 7.959 ms | 2.61× |
| 64 | 1.53e-7 | 5.568 ms | 16.198 ms | 2.91× |

The first nested integer-reduction formulation passed JVM tests but failed the PTX device gate. A
flattened correctness fallback passed but was slower than the Vector API. Explicitly expressing the
16 packed Q4 pair products preserved integer arithmetic, passed the device gate, and produced the
measurements above. The qualification threshold was never weakened.

For comparison, the simpler Q8_0-by-F32 experiment reached 2.70× at batch 1 and 10.61× at batch 32
against the same two-vCPU host. Q4_0 is the more relevant result because it exercises the activation
quantization and packed arithmetic used by published Q4_0 models.

## Full Qwen model result

The 30-token prompt has a deterministic expected answer of `JAVA` on both paths.

| Path | Prefill | TTFT | Total | Output |
|---|---:|---:|---:|---|
| A16 host, Vector API cold | 2.348 s | 2.360 s | 2.549 s | `JAVA` |
| A16 host, Vector API warm | 1.154 s | 1.155 s | 1.265 s | `JAVA` |
| A16 host, Tornado cold | 9.058 s | 9.060 s | 9.193 s | `JAVA` |
| A16 host, Tornado warm | 0.488 s | 0.489 s | 0.623 s | `JAVA` |
| 8-vCPU EPYC, Vector API warm | 0.574 s | 0.576 s | 0.651 s | `JAVA` |

The provider created 191 persistent projection plans. Compilation dominates its first request;
after compilation, prefill is 2.36× faster than the same host's warm Java path. Against the stronger
eight-vCPU control, this small model and short prompt are close: GPU total latency is only about 4%
lower.

The 250-token case produces identical text on CPU and GPU, although the tiny model does not follow
the requested one-word format. This case measures parity and throughput, not answer quality.

| Path | Warm prefill | Warm total |
|---|---:|---:|
| A16 host, 2-vCPU Vector API | 9.537 s | 9.928 s |
| A16 host, Tornado | 4.759 s | 5.047 s |
| 8-vCPU EPYC, Vector API | 4.951 s | 5.076 s |

The longer prompt required two batch shapes and 382 persistent plans. The 2 GiB A16 slice again
roughly matches the stronger CPU rather than decisively beating it.

## Decision

The experiment proves that a Java-authored, in-process GPU backend is technically viable and can be
injected through the existing Models SPI without changing user inference code. It is not ready to
publish:

- first-request compilation is much slower than the current backend;
- Q4 acceleration alone leaves attention and other Java work as the full-model limit;
- plan reuse or ahead-of-time caching is needed to avoid one compiled plan per tensor and batch
  shape; and
- qualification must cover larger GPU allocations and additional vendors before choosing automatic
  eligibility thresholds.

The next experiments should retain the Java-first approach: reduce plan multiplicity, move Q8
activation preparation to the device, fuse Q/K/V and gate/up projections, then measure attention and
KV-cache kernels. A larger Vultr A16 allocation was provisioned for the control but completed in a
stopped state and would not accept a power-on request; it was deleted without producing data.
